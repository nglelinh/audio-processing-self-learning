Web deployment of neural noise suppression stands or falls on **WebAssembly** throughput. **SIMD** (single instruction, multiple data), the 128-bit `simd128` feature, threads where the page is allowed to use them, and the MIME type of the `.wasm` response often matter as much as the choice of model. Package `deepfilternet3-noise-filter` **≥ 1.2.0**, including **1.3.0**, ships a WASM build with SIMD enabled. The package README attributes about **20–30%** higher speed to that build. That figure is the README’s claim, not a measurement from this course. This lesson shows how to detect the feature, how Safari 16.4 bounds it, and how an AudioWorklet stays inside its budget when SIMD is missing.

## Core explanation

### What SIMD changes in the hop

Matrix multiplies and convolutions dominate a DeepFilter-class hop. SIMD loads 128 bits, four `f32` lanes or eight `i16` lanes, and raises arithmetic throughput. The real-time factor of a hop of duration \(H\) is

$$
\mathrm{RTF} = \frac{T_{\mathrm{wall}}}{H}.
$$

\(\mathrm{RTF} < 1\) is required on that device and still not sufficient: the AudioWorklet also spends time on the STFT, copies, and the encoder. The package README says the SIMD build is about 20–30% faster for versions ≥ 1.2.0. Illustratively, a hop at RTF \(0.90\) would land near \(0.63\)–\(0.72\) if that claim holds on your laptop. Confirm with your own percentiles. Do not quote 20–30% as a lab result.

The public WASM recipe in the repository README enables this at build time: `wasm-opt` flags include `--enable-simd`, `--enable-bulk-memory`, and `--enable-nontrapping-float-to-int`, and `RUSTFLAGS` adds `+simd128`. Versions ≤ 1.1.2 were built without that feature set. You do not need a compiler for this lesson. You do need to know that a module compiled with `simd128` **fails to instantiate** on an engine that lacks the feature. It does not silently run slower.

### Browser floor, especially Safari 16.4

The same README states the SIMD build needs **Chrome 91+**, **Firefox 89+**, and **Safari 16.4+**. Safari 16.4 is a hard boundary, not a tuneable flag. Safari 16.3 and earlier, including iOS versions that ship that engine, reject the SIMD module at compile or instantiate time. There is no “partial SIMD” mode that runs the 1.3.0 module slowly. Product policy is explicit: detect, then fall back to a non-SIMD artifact (the ≤ 1.1.2 style build, or browser APM noise suppression, or bypass). `DeepFilterNoiseFilterProcessor.isSupported()` only checks that `AudioContext` and `WebAssembly` exist. It does **not** prove `simd128`. A page can pass `isSupported()` and still fail inside `initialize()` when `WebAssembly.compile` rejects the module.

A maintained probe, which validates on engines with SIMD, is:

```javascript
const simd = WebAssembly.validate(new Uint8Array([
  0, 97, 115, 109, 1, 0, 0, 0, 1, 5, 1, 96, 0, 1, 123, 3, 2, 1, 0,
  10, 10, 1, 8, 0, 65, 0, 253, 15, 253, 98, 11
]));
```

Prefer this style of probe, or the helper your runtime documents, over a hand-written opcode list you have not validated.

### Threads are a separate privilege

Multi-threaded WASM needs `SharedArrayBuffer`, which modern browsers expose only on a cross-origin-isolated page (COOP and COEP headers). Many product origins cannot set those headers. Design the real-time budget for **one** WASM thread first. Threads are an optimization after isolation is real, not part of the README’s SIMD percentage.

### AudioWorklet meets the module

`DeepFilterNet3Core.initialize()` compiles WASM on the main thread. `createAudioWorkletNode` then constructs an `AudioWorkletNode` named `deepfilter-audio-processor`. Do that before audio is flowing. The worklet must not compile a multi-megabyte module inside `process()`. Keep the heap stable: per-quantum allocations across the JS/WASM boundary blow the budget you just won with SIMD. STFT and windowing outside the graph need the same discipline. Profile them separately from inference.

### Three strings, two failures

The mini-lab classifies three deployment strings. `simd128` is the feature the ≥ 1.2.0 module requires, so on a browser inside the README floor it is not a failure. `missing simd` fails closed: the module does not instantiate. `wrong wasm mime` fails when a loader uses streaming compilation and the response is not `application/wasm`. The 1.3.0 core compiles an `ArrayBuffer` from `fetch`, which is less sensitive to MIME than `instantiateStreaming`, but a CDN must still serve `df_bg.wasm` as `application/wasm`. Proxies that sniff a wrong type, and any future streaming path, will break the pair of files from lesson 07-03.

### Graceful degradation

```text
if missing simd or wrong wasm mime or RTF p95 over budget:
    fallback = non-SIMD build OR browser APM NS OR bypass
```

Never leave a crackling worklet as the success path. `setNoiseSuppressionEnabled(false)` on `DeepFilterNet3Core`, or `await filter.setEnabled(false)` on `DeepFilterNoiseFilterProcessor`, is the bypass once the node exists. If compile itself throws, do not publish a half-built processor. Publish the unprocessed track and surface one non-blocking error (lesson 07-02).

## Mini-lab

No compiler. Run `python3 simd_fail.py`.

```python
checks = {
    "simd128": "pass",
    "missing simd": "fail",
    "wrong wasm mime": "fail",
}
failed = {name for name, status in checks.items() if status == "fail"}
print(sorted(failed))
```

Sorting makes the set printable and stable. The set itself is `{"missing simd", "wrong wasm mime"}`.

**Expected**

```text
['missing simd', 'wrong wasm mime']
```

**Failure modes**

- Printing the set without sorting. Hash randomization can reorder the line; the expected check uses `sorted`.
- Treating Safari 16.3 as “SIMD but slower.” The README boundary is 16.4; earlier Safari fails the module.
- Assuming `isSupported()` covers `simd128`. It does not.
- Serving the WASM file as `text/plain` and debugging the model archive instead.

## Pitfalls

- Testing only desktop Chrome, which has had SIMD for years.
- Forgetting that iOS Safari follows the 16.4 line.
- Shipping an `-O0` or debug WASM to production.
- Turning on threads without COOP/COEP and calling the hang a model bug.
- Quoting the README’s 20–30% as if this course measured it.

## Exercises

1. Run the SIMD `validate` probe in two browsers and record pass or fail beside the version string.
2. If a scalar build sits at RTF p95 \(1.1\) and a SIMD build at \(0.45\), what do you ship to Safari 16.3?
3. Explain COOP/COEP in a short note to a web lead who cannot change the origin headers this week.
4. Propose how to time STFT and inference separately inside the worklet.
5. Why does a wrong MIME type belong in the failure set even though `WebAssembly.compile` on an `ArrayBuffer` does not check `Content-Type`?

### Answer hints

1. Chrome 91+ and Firefox 89+ should pass. Safari passes at 16.4 and fails before that.
2. Do not ship the SIMD module there. Bypass, APM noise suppression, or a non-SIMD artifact. The 0.45 number is unreachable if instantiate fails.
3. Threads need cross-origin isolation. Until headers exist, budget a single thread.
4. Post timestamps from the worklet for the STFT section and the inference section. Aggregate p95 on the main thread. Do not `console.log` every quantum.
5. Streaming instantiation and intermediaries require `application/wasm`. The lab fails that string so the CDN contract stays explicit.
