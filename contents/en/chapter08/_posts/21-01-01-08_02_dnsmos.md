Customer calls do not ship with a clean reference, so SI-SDR is undefined on the audio you most need to judge. DNSMOS is the non-intrusive predictor associated with Microsoft’s Deep Noise Suppression Challenge: a network that estimates a mean-opinion score from the enhanced signal alone. Reddy, Gopal, and Cutler published DNSMOS at Interspeech 2021 and DNSMOS P.835 at ICASSP 2022. Both are tools for ranking clips inside a frozen domain. Neither is an official pass/fail threshold, and a move of a few hundredths is not a ship decision by itself. This lesson shows how to pin a version, how domain shift breaks the score, and how to file the number next to listening notes.

*Figure. DNSMOS occupies the non-intrusive column. It does not need $$s$$. It still does not replace a listening test when the noise or the language leaves the training domain.*

## What you should be able to do

You should be able to say when DNSMOS is the right column (no clean $$s$$), name the two papers without inventing a cutoff, and design a small golden set whose **deltas** you can re-run after a suppression-level change. You should also list the domain shifts that make a higher score the wrong product call.

## Where it sits in the stack

| Setting | Clean reference? | What you can compute |
|---------|------------------|----------------------|
| Synthetic DNS-style mixture | Yes | SI-SDR, and PESQ or STOI if you choose to install them |
| Real laptop or phone recording | No | DNSMOS (version pinned) and a listening note |
| Ship review | Sometimes a tiny labeled subset | Predictor deltas **and** humans, plus RTF |

The challenge data, baselines, and blind sets live in [microsoft/DNS-Challenge](https://github.com/microsoft/DNS-Challenge). Challenge years do not share one metric list. When you write “DNSMOS” in a table, write the predictor build you ran (P.808-style DNSMOS versus DNSMOS P.835) and the checkpoint filename. Scores from two checkpoints are not one time series.

## What the predictor returns

DNSMOS reads one waveform and returns a scalar, or a small tuple of scalars in the P.835 variant (signal quality, background noise, and overall). It does not see the clean studio take, so it cannot punish a time shift the way SI-SDR does, and it cannot tell you ΔSI-SDR. It is happy to score a file that is mostly silence if you let that file dominate the mean. It is an offline batch tool. It is not a substitute for the realtime telemetry in Chapters 05–07: init time, fallback when the CDN misses, and RTF inside the audio callback.

P.835 separates speech quality from background noise. That split matters when the noise floor is quiet and the voice is thin. Report the components you actually have. This course does not publish an official DNSMOS pass line. If your team picks an internal epsilon, label it as a lab policy on a named golden set, not as a property of the paper.

## Domain shift is the failure mode

The networks were trained to track listening labels from challenge-like speech and noise. A Mezon meeting is a different generator. Treat these as breaks:

1. Language and accent. A model that tracked English challenge listeners can move for the wrong reason on Vietnamese speech, regional tone, or code-switching.
2. Codec. Opus at a low bitrate already sounds rough. The predictor may charge that roughness to your noise suppressor.
3. Non-speech. Music, notification chirps, and screen-share audio are outside the speech-enhancement domain the challenge optimized.
4. Aggressive suppression. Some predictors reward a quieter residual even when consonants are gone. Users do not.
5. Bandwidth. A 16 kHz file and a 48 kHz file are different inputs. Resample with a written rule, or score each rate in its own column.

Freeze a golden set: café babble, keyboard, fan, a quiet room, and one clip with residual echo if the product still has any. Store the wavs, the DNSMOS version, and the enhancement command. Track the **change** against the pinned package (`deepfilternet3-noise-filter` 1.3.0 or the version you actually run), per condition, with the clip count visible. A mean that moves because one silent file was added is not a model win.

## How to combine columns

Use SI-SDR on synthetic twins when you have them (08-01). Use DNSMOS on the real golden set. Use a blinded AB or a small MUSHRA-like pass (08-03) on the same conditions before you change the default of `setSuppressionLevel`. Keep RTF p95 next to the quality numbers so a “better” MOS that misses the AudioWorklet deadline is visible. Ship when the real-set delta and the listening note agree and the realtime budget still holds. A peak on synthetic SI-SDR alone is a research note, not a release.

A CI sketch, still conceptual until you own the machines:

```text
on a change that can alter audio:
  use the pinned golden wavs (git-lfs or a versioned archive)
  enhance offline with the same level and sample rate
  run the pinned DNSMOS checkpoint
  upload the CSV
  fail only on a lab epsilon you wrote down for this set
```

Do not let CI download an unbounded noise corpus. Do not fail the build because a paper abstract once showed a score near 3. Something. That number is not your epsilon.

## Mini-lab

Create `dnsmos_plan.md` for a no-reference folder. You are not required to run the DNSMOS weights in this lab (they are a separate download and a version pin). You are required to show that every real clip has an explicit `n/a` plan for SI-SDR and a named DNSMOS variant.

```text
golden/
  cafe__laptop.wav
  keyboard__laptop.wav
  fan__phone.wav
  quiet__laptop.wav
dnsmos_plan.md
```

Put this table in `dnsmos_plan.md`:

```markdown
| clip id | condition | SI-SDR | DNSMOS variant | why this clip can fool the predictor |
| cafe__laptop | babble, no clean ref | n/a | P.835 or the build you will pin | overlapping talkers |
| keyboard__laptop | key clicks | n/a | same build | impulsive noise, not the challenge average |
| fan__phone | stationary hum | n/a | same build | phone bandwidth |
| quiet__laptop | clean-speech control | n/a | same build | over-suppression on an already quiet file |
```

Expected output of `python3 check_dnsmos_plan.py` after you save the file:

```python
from pathlib import Path
text = Path("dnsmos_plan.md").read_text().lower()
need = ["n/a", "p.835", "cafe__laptop", "keyboard__laptop", "fan__phone", "quiet__laptop"]
missing = [n for n in need if n not in text]
print("missing", missing or "none")
```

```text
missing none
```

Failure modes: writing a numeric SI-SDR for a real file that has no clean reference; mixing P.835 and the 2021 DNSMOS scalar in one mean; dropping the quiet control so over-suppression cannot be seen; treating any absolute score as an official Microsoft cutoff.

## Exercises

1. In four sentences, state the policy “when this team runs DNSMOS,” including version pin, golden-set path, and the ban on an official threshold.
2. Give three domain shifts that matter for a Vietnamese meeting app using `DeepFilterNoiseFilterProcessor`, and one clip filename for each.
3. A golden-set mean rises by 0.05 after you change `setSuppressionLevel`. What extra table would you demand before calling it an improvement?
4. Explain why DNSMOS on a stereo mix, or on a file that is half silence, can look strong while the call sounds worse.
5. Name the column you will leave as `n/a` on these four files, and the column you will leave as `n/a` on a synthetic pair when the DNSMOS weights are not installed.

### Answer hints

1. Run one named build (DNSMOS or DNSMOS P.835). Store deltas on a frozen set. Any epsilon is local policy. Reddy, Gopal, and Cutler did not hand you a ship line.
2. Plausible shifts: tonal Vietnamese speech, Opus artifacts, fan-plus-keyboard rooms, Zalo/Meet-style device mics. Filenames should encode noise and device.
3. Per-condition means and clip counts, not one average. Then a blinded listen on the condition that moved.
4. The predictor scores what it sees. A downmix can hide a bad channel. Silence inflates a mean if you do not gate it.
5. Real files: SI-SDR is `n/a`. Synthetic files without the checkpoint: DNSMOS is `n/a`. Do not backfill either cell.
